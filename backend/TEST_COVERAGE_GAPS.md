# Backend Test Coverage Gaps

This is the backend's coverage work-tracking document: the measured state of
`app/` under the test suite, which branches the tests exercise, and the gaps
that are still open. It is deliberately split into two halves with different
trust levels.

**Machine-generated.** Every percentage, statement count and uncovered-line
list in the *Measured coverage* section below is produced by a run of the suite.
`python scripts/measure_coverage.py` re-measures and fails when that block no
longer matches the tree, so those numbers cannot quietly go stale.

**Hand-written.** The per-module checklists and the open-gaps list below. They
deliberately carry no coverage percentages — a percentage in prose would be a
second, ungated copy of the truth — and
`tests/test_coverage_doc.py` checks the open-gaps list against the generated
table: a module with uncovered statements may not be missing from it, a fully
covered module may not appear in it, every `lines A-B` it cites must be inside
that module's uncovered lines, and no line outside the generated block may pair
a specific `app/<module>.py` reference with a percentage at all.

## Why this split

This document used to assert that "every `app/*.py` module is at 100% coverage
(2174 statements, 0 missed)" and that all error paths across the codebase were
covered. Re-measuring the tree showed the assertion to be false, and the hole
was concentrated in two modules the document did not mention at all —
`app/recommender.py` and `app/user_profile.py` (#295). The figures quoted in
that audit are deliberately not repeated here: they were taken from a tree that
has changed since, so they are not reproducible. The figures that follow are.

An asserted number nobody recomputes is worse than no number: it reads like a
guarantee, and it is what let `main.py`, `chat.py`, `query_intent.py`,
`health.py`, `recommender.py` and `user_profile.py` change underneath a
document that claimed to have measured them. The figures are now derived rather
than claimed, and a document that drifts fails the build.

## Re-measuring

```sh
cd backend
python -m pytest --cov=app --cov-report=term-missing   # the measurement itself
python scripts/measure_coverage.py                     # exit 1 if this file is stale
python scripts/measure_coverage.py --write             # regenerate the block below
```

`pytest-cov` is pinned in `requirements-dev.txt`, so the measurement reproduces
from a clean install of the pinned dependencies. The gate re-runs the same suite
with `--cov-report=json` and compares the result module by module, so a
hand-edited percentage, a deleted module row, a stale uncovered-line list, or a
new `app/*.py` module that nobody wrote a row for all fail the backend CI job.
Never edit the generated block by hand: change the code or the tests, re-run
`--write`, and commit the regenerated block with the change that caused it.

## What the numbers do and do not mean

Statement coverage is a floor, not a goal. 100% of statements means every line
ran at least once; it does not mean a single assertion would notice if the line
returned the wrong value. A module with no uncovered statement is a floor, not
a proof, and no other part of this document should be trusted on its behalf —
read the checklist to see what is actually asserted.

The `**ERROR PATH**` markers in the checklists record which failure modes a
test *simulates*. Two different claims hide behind that marker:

* In a module the measurement puts at 100%, the marker is measurement-backed —
  the statements really did execute.
* In a module listed in the open gaps below, the marker is only a claim about
  one site, and the generated list of uncovered error-handling statements is
   the authority on what is *not* exercised. Where the two disagree, the
   generated list wins.

### app/cost_budget.py (covered by tests/test_cost_budget.py + tests/test_budget_lua.py)

The cap is RESERVE / SETTLE / RELEASE around every billed call; the whole
read-modify-write lives in one Lua script (`_BUDGET_LUA`) over four keys
(day counter, live holds, holds expiry zset, holds-accounted ledger). The
Python side is covered against `FakeBudgetStore`, a model of that contract;
the shipped script itself is EXECUTED by `tests/test_budget_lua.py` under
`lua5.1` (skipped where lua5.1 is absent), so the two cannot drift apart
without a failure.

- [x] **`reserve` hold + rejection**: hold written and counted
      against the cap for the next caller; a rejected reserve leaves no hold
      behind; cap disabled (`LLM_DAILY_BUDGET_USD <= 0`) touches no store;
      hold floored at 1 micro-USD so a zero `LLM_CALL_RESERVE_USD` cannot turn
      the cap into a no-op; first `BudgetExceeded` logs one warning.
- [x] **`reserve` store down → `BudgetUnavailable`**: fails
      closed, is not a `BudgetExceeded`, and drops the cached script handle.
      **ERROR PATH — Redis down.**
- [x] **`settle` counter write**: actual cost recorded whole
      (hold was never counted), over-reserve recorded and blocking the next
      call, zero-cost settle records nothing, empty id list still bills,
      store-down leaves the holds in place. **ERROR PATH — Redis down.**
- [x] **`settle` idempotency + crash promotion** (Lua sweep/settle arithmetic):
      settling the same ids twice charges once, duplicate ids within one call
      charge once, a hold that lapsed is CHARGED to the counter (a crash is
      not free spend) and its later settle REPLACES the estimate with the real
      cost rather than adding to it.
- [x] **crash promotion is REACHABLE, not just arithmetically correct**: the
      holds hash and the expiry zset are expired at twice the reservation TTL,
      because a hold's zset score first satisfies the sweep predicate exactly

## Error-path status

The generated block above lists, by module, every `except` and `raise`
statement that no test executes. That list is the answer to "are the error paths
covered?" — the opposite of what the previous version of this document did,
which asserted that all of them were while the measurement said otherwise.

The untested error paths, grouped by the failure that would have been caught:

* **Qdrant unreachable, or a filter/query typo.** The whole body of
  `get_similar_articles`, `get_trending_feed` and
  `get_personalized_recommendations` in `app/recommender.py`, including each of
  their catch-alls, plus the whole of `retrieve_by_date_window` in
  `app/main.py`. A wrong `FieldCondition` or a changed `query_points` argument
  returns an empty or mis-ranked feed for every user, silently.
* **Redis down, or returning malformed data.** The `down` and `degraded` legs
  of `_redis_status` in `app/health.py`; the corrupt-payload degradation in
  `HybridCache.get`; the `int()` casts and their fallbacks in `record_click` in
  `app/analytics.py`; the `Retry-After` parsing and the empty-`choices`
  `LLMUnavailableError` in `app/llm.py`; the whole `get_trending_articles`
  Redis scan and the profile-vector validation `TypeError`/`ValueError` in
  `app/user_profile.py`.
* **A malformed or legacy row.** The unconnected-store `raise` and
  `delete_message` in the store in `app/chat.py`, the sized-less-iterable
  `except TypeError` in `_container_stub`, and the policy-violation hint in
  `_password_hint` in `app/auth.py`.
* **A bad deployment value.** The `ValueError` in `_parse_allowed_hosts` is the
  only statement without a test in `app/config.py`, and it is the guard that
  rejects an unusable `ALLOWED_HOSTS` entry at import time.
* **A mid-turn failure in the chat path.** `send_message`'s generic
  `except Exception` — the one that rolls back the dangling user message before
  re-raising — and six returns in `send_message_stream`, one of them a
  `release(holds)`.
* **A defect in the probe machinery itself.** The `except Exception` in
  `ready_deep`, which is the code that must refuse to launder a probe failure
  into a verdict about the dependencies.

   and a defect there is invisible both to the user and to the suite.
2. `app/user_profile.py` — the trending scan and the cold-start profile build,
   which is where a new user's first recommendations come from.
3. `app/main.py` and `app/query_intent.py` — the date-windowed retrieval, the
   facet-relaxation retry and the relative-range parsing, all on the search
   path itself.
4. The remainder, which is small and mostly a single branch each.

Adding a test for one of these is a normal change: re-run
`python scripts/measure_coverage.py --write` in the same commit, so the table
and the gap list move together, and the gate stays green only if both did.
